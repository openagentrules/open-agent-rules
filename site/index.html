Open Agent Rules is a portable document format for agent guardrails. A rule names a lifecycle moment, a condition over typed observations, and an effect. The same document produces the same decision on every conforming engine.

Why Open Agent Rules

The problem

Agent guardrails today are code. A callback registered with a gateway, a plugin class, a Python predicate that receives a request object and returns a verdict. That has four costs, and they compound.

A security reviewer cannot read it. Reviewing a guardrail means reading a function, then the helpers it calls, then the state it closes over — and the reviewer still cannot tell which requests it will fire on.

It cannot be diffed. "We tightened the scope check" is a code diff, not a policy diff. There is no artifact whose change history is the change history of the policy.

It cannot be tested without the host. The predicate takes the host's own request object, so exercising it means standing up the host. In practice that means guardrails are tested by running the agent and watching.

And it cannot be moved. Every gateway, every agent framework, every tool server has its own callback signature and its own request shape. A guardrail written for one is a rewrite for the next.

The goal is one sentence: a guardrail should be a document you can read, diff, test, and move.

Observation, not verdict

The idea that makes this work is a division of labour:

The host produces facts. The rule composes facts. The engine renders effects.

A fact is an observation the host publishes about its own state — typed, named, and free of judgement. unobserved_cited_paths is a fact: it is a list of paths the agent cited and the host never saw it read. synthesis_is_ungrounded is not a fact. It is a conclusion, and the moment a host publishes it, the policy has moved back into the host's code where nobody can read it.

The distinction is not stylistic. The threshold and the composition are the policy — they are the parts an operator argues about, tunes, and audits. So they have to live where a reviewer can see and change them:

when: "prompt_injection_score > 0.8 && !session_is_internal"

Everything about that line is reviewable. The detector produced a number; the rule decided that 0.8 is the bar and that internal sessions are exempt. Move the threshold into the detector and the same policy becomes invisible.

This is why the specification states observation-not-verdict as a requirement on fact providers rather than as advice. A format whose facts may contain verdicts degenerates into the callback model with extra syntax.

One rule, annotated (non-normative)

spec_version: "1.1"
id: READ_OUTSIDE_SCOPE          # stable; the identifier the decision carries
kind: policy                    # fixes evaluation order, nothing else
on: tool.pre_invoke             # a core anchor: before the tool runs
selector:
  tools: [read]                 # clauses are AND; omitting one is permissive
when: 'path_outside_scope("read")'   # composition of observations
effect: block                   # what the engine does when the condition holds
on_error: fail_closed           # if this cannot be evaluated, block
what: "The call reads outside the declared scope."
fix: "Read inside scope, or widen the scope deliberately."

Six lines carry the whole policy, and the last two carry the explanation the caller sees. on and selector say where; when says whether; effect and on_error say what happens, including when the check itself fails. Clause references: [OAR-SEL-2], [OAR-EVAL-4], [OAR-OPS-2].

Why not Rego, or Cedar

Rego and Cedar are mature, well-tooled, and more expressive than anything here. They are also solving a different problem, and the difference is the whole point.

Both evaluate arbitrary policy over arbitrary input. That generality is their strength for authorisation, and it is exactly what stops a guardrail from travelling: every deployment invents its own input document. A Rego policy for one agent runtime reads input.request.tool.name; the next reads input.action.id. Both are valid Rego. Neither rule runs on the other's system, and neither can be tested without that system's input shape.

Open Agent Rules fixes the two vocabularies that generality leaves open: the lifecycle moments (core anchors) and the typed observations (the fact tiers). That is a real loss of expressiveness, and it buys three things nothing else on the list has — a rule that runs unchanged on another engine, a rule that can be tested against a published fixture corpus without the host, and a rule whose complete input surface is enumerable.

What they do better: maturity, tooling, formal analysis (Cedar's decisions are verifiable), and expressiveness for policies that are not agent guardrails. If your problem is authorisation over your own resource model, use Cedar. If it is "what may this agent do at this moment", the vocabularies are the value.

A note on the condition language: this specification's normative content is the document model, the profiles, and the decision semantics. when is written in a CEL subset because CEL is a good fit for side-effect-free boolean composition, but a host is free to evaluate the same document model with another expression language, provided the observable decision is the same. The corpus is what settles whether it is.

Why not a plugin or callback guardrail API

The incumbent shape in agent gateways and content-safety products is registration: you write a class or a function, register it under a hook name, and it returns a verdict.

It is the same problem as §1, aimed at a friendlier surface. The plugin owns the verdict, so the threshold, the exemptions, and the scoping all live inside code. That makes the policy unreadable to anyone who is not reading the source, untestable without running the host, and non-portable by construction, since the plugin is written against the host's own hook signature and request object.

Open Agent Rules does not replace that seam — it inverts it. A detector is still code, and still a plugin. What changes is that the detector returns observations and the rule owns the decision. You keep the extensibility and get a policy you can read.

How to check your implementation

Three commands, no account, no monorepo:

curl -O https://openagentrules.org/spec/1.1/oar.schema.json
curl -O https://openagentrules.org/spec/1.1/conformance/manifest.json
npx @openagentrules/oar-ref ./conformance

Read the numbered runner algorithm in section 9 of the specification, implement it, and run the corpus. Every fixture names the clauses it exercises, so a failure tells you which sentence you and the specification disagree about. If you conclude the specification is wrong, open an issue quoting the clause id — that is what they are for.
