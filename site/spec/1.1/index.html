Open Agent Rules

Version 1.1 · Status: published · Canonical URL: https://openagentrules.org/spec/1.1/

Open Agent Rules (OAR) is a portable document format for agent guardrails. A rule is a document — not code — that names a lifecycle moment, a condition over typed observations, and an effect. A conforming engine loads the document, evaluates the condition, and renders the effect. The same document produces the same decision on every conforming engine.

Implementation grant

Anyone may implement this specification, for any purpose, without permission, notification, or fee. See LICENCE-SPEC.md for the licence covering this text.

Conformance language

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119. Every requirement carries a stable clause identifier in the form [OAR-AREA-n]. Clause identifiers are append-only: they are never renumbered and never reused. Examples are non-normative unless a clause identifier appears beside them.

1. Overview

A rule is a document with three obligatory parts: where it applies (an anchor plus a selector), when it applies (a condition over facts), and what happens (an effect, plus optional engine side-effects). Everything else in the document is metadata, presentation copy, or provenance.

The division of labour is fixed and is the reason the format stays readable:

The host produces facts. The rule composes facts. The engine renders effects.

A host is the system being guarded — an agent runtime, a model gateway, a tool server. It publishes typed observations of its own state at named lifecycle moments. An engine loads rule documents, selects the ones bound to the moment that just occurred, evaluates their conditions against the published observations, and applies the resulting decision. A rule author writes documents; they never write host code.

Portability in this specification is a precise claim, not a marketing one. Two vocabularies are fixed by the standard: a small set of core anchors (lifecycle moments every conforming host has) and a tiered fact catalogue (observations every conforming host publishes). A rule that uses only those travels unchanged between conforming engines. A rule that reaches for a host's own anchors or its own facts is still a valid OAR document and is still loadable — it is simply not portable, and the standard says so rather than pretending otherwise.

2. Document model

  • [OAR-DOC-1] A rule document MUST be representable as a JSON object. An engine MAY accept other serialisations (YAML is the common authoring form) provided the mapping to JSON is lossless; interchange between implementations MUST use JSON.
  • [OAR-DOC-2] A rule document MUST contain spec_version, id, kind, on, selector, and effect. An engine MUST reject a document missing any of them.
  • [OAR-DOC-3] spec_version is a string of the form <major>.<minor>. An engine MUST reject a document whose major version it does not support, and MUST NOT silently downgrade or coerce it. An engine that supports major version 1 MUST accept "1.0" and "1.1".
  • [OAR-DOC-4] id is a stable identifier matching ^[A-Z][A-Z0-9_]*$. It MUST NOT be reused for a rule with a different meaning once published.
  • [OAR-DOC-5] title is an optional human-readable label. It MUST NOT affect any decision.
  • [OAR-DOC-6] kind MUST be one of schema, policy, invariant, detector. It fixes evaluation order and nothing else — see [OAR-EVAL-2].
  • [OAR-DOC-7] severity is optional, one of block, warn, info, and is telemetry and presentation only. An engine MUST NOT let severity affect selection, condition evaluation, ordering, precedence, or the returned decision. Two rules differing only in severity MUST produce identical decisions.
  • [OAR-DOC-8] effect MUST be one of block, warn, nudge, allow, transform.
  • [OAR-DOC-9] when is an optional condition expression over the declared fact environment (section 5). When absent, the rule's condition is satisfied.
  • [OAR-DOC-10] flow is an optional ordered list of step names. When present, the rule fires only if flow matches the recent activity window as described in [OAR-FACT-10].
  • [OAR-DOC-11] enforcement is optional, one of enforce, monitor. Its default MUST be enforce.
  • [OAR-DOC-12] mandatory is an optional boolean. Its default MUST be false.
  • [OAR-DOC-13] on_error is optional. Its value MUST be fail_closed, fail_open, or a rule identifier to substitute. Its default MUST be fail_closed.
  • [OAR-DOC-14] on_fire is an optional list of declared engine side-effects drawn from the closed vocabulary in section 6. Its default MUST be the empty list.
  • [OAR-DOC-15] stream is optional, one of buffered, chunk. Its default MUST be buffered.
  • [OAR-DOC-16] references is an optional object of interoperability taxonomy tags. It MUST NOT affect any decision.
  • [OAR-DOC-17] detector is an object carrying a ref. A document with kind: detector MUST carry it; a document with any other kind MUST NOT.
  • [OAR-DOC-18] A document MAY carry presentation copy describing the finding and the remedy. Copy fields MUST NOT affect selection, evaluation, ordering, or precedence.

2.1 Fields added in 1.1

Every field in this subsection is optional, so every valid 1.0 document remains a valid 1.1 document.

  • [OAR-DOC-19] tools is a deprecated top-level list of tool names retained from earlier revisions. An engine MUST continue to accept it and MUST treat it as equivalent to selector.tools when selector.tools is absent. New documents SHOULD use selector.tools.
  • [OAR-DOC-20] A document MAY carry implementation extension fields whose names begin with x-. An engine MUST ignore an x- field it does not recognise, and MUST reject a document carrying any other field this specification does not define. An x- field MUST NOT become normative without a specification change.
  • [OAR-DOC-21] namespace is an optional publisher scope matching ^[a-z0-9]([a-z0-9-]*[a-z0-9])?(\.[a-z0-9]([a-z0-9-]*[a-z0-9])?)*$. It identifies the organisation publishing the rule.
  • [OAR-DOC-22] The identity of a rule is the pair (namespace, id). An absent namespace means the loading host's own scope. Two documents sharing an id under different namespaces MUST NOT collide. The identifier an engine renders in its decision, and that downstream software branches on, remains the bare id — see [OAR-EVAL-7].
  • [OAR-DOC-23] requires_facts is an optional list of fact names the rule needs. An engine that does not provide one of them MUST reject the rule at load, naming both the rule and the fact, rather than failing condition compilation or evaluating a default value.
  • [OAR-DOC-24] profile is an optional informational string, one of portable or host, recording the author's intent. An engine MUST NOT derive behaviour from it; the portability of a rule is determined by its anchor and its facts, not by this field.
  • [OAR-DOC-25] code, an alias of id in revision 1.0, is deprecated. An engine MUST accept it when spec_version is "1.0" and MUST reject it when spec_version is "1.1" or later.

2.2 Example (non-normative)

{
  "spec_version": "1.1",
  "id": "READ_OUTSIDE_SCOPE",
  "title": "Read outside the declared scope",
  "kind": "policy",
  "on": "tool.pre_invoke",
  "selector": { "tools": ["read"] },
  "when": "path_outside_scope(\"read\")",
  "effect": "block",
  "on_error": "fail_closed"
}

3. Anchors and selection

An anchor names a lifecycle moment at which an engine evaluates rules. A selector narrows a rule to a subset of the occurrences of that moment.

  • [OAR-SEL-1] on MUST name exactly one anchor. An engine MUST reject a document whose on it cannot resolve, naming the value.
  • [OAR-SEL-2] Selector clauses are conjunctive: a rule is selected only when every clause present in its selector matches.
  • [OAR-SEL-3] An omitted clause is permissive — it imposes no constraint. An empty selector therefore matches every occurrence of the anchor.
  • [OAR-SEL-4] At an anchor occurrence, an engine MUST select exactly those rules whose resolved on equals that anchor and whose selector clauses all match.
  • [OAR-SEL-5] Selector clauses match machine-observable state only. An engine MUST NOT match a selector clause against natural-language text, and MUST NOT infer a clause value from prose shape, keyword lists, or substring search.
  • [OAR-SEL-6] A selector clause naming a dimension the host does not model MUST NOT match. The rule is therefore not selected; this is not a load error and not a runtime error.
  • [OAR-SEL-7] The selector vocabulary is closed and published as a schema. An engine MUST reject a document carrying a selector clause the schema does not define.

4. Evaluation

  • [OAR-EVAL-1] An engine MUST evaluate selected rules in a deterministic order: ascending by kind in the sequence schema, policy, invariant, detector; then ascending lexicographically by id.
  • [OAR-EVAL-2] kind carries no evaluation meaning beyond that order. An engine MUST NOT derive a threshold, a weight, or a decision from kind, and this specification does not define a separate priority field.
  • [OAR-EVAL-3] The first selected rule that fires with effect block or transform MUST short-circuit the anchor occurrence: no later rule in the order is evaluated.
  • [OAR-EVAL-4] An engine MUST resolve the decision for an anchor occurrence by precedence: if any rule fired with block, the decision is block; otherwise if any fired with nudge, the decision is nudge; otherwise if any fired with warn, the decision is warn; otherwise the occurrence is allowed.
  • [OAR-EVAL-5] A rule firing with allow contributes no decision. It records an explicit pass and MUST NOT override a block, nudge, or warn from another rule.
  • [OAR-EVAL-6] A decision MUST carry, at minimum, the effect and the identifier of the rule that produced it. It MAY carry a data map for rendering and the list of side-effects that were applied.
  • [OAR-EVAL-7] The identifier carried by a decision MUST be the bare id of the rule (or the substitute identifier selected by on_error). Software consuming a decision MUST branch on that identifier and MUST NOT branch on any human-readable message text.
  • [OAR-EVAL-8] A rule whose enforcement is monitor MUST NOT short-circuit the anchor occurrence, whatever its effect. Evaluation continues with the next rule in the order.
  • [OAR-EVAL-9] An engine MUST apply the on_fire side-effects of every rule that fired and was enforced, including rules whose effect lost precedence under [OAR-EVAL-4]. Side-effects of rules never reached because of a short-circuit MUST NOT be applied.

5. Facts and conditions

  • [OAR-FACT-1] The fact environment is closed and typed: an engine MUST declare the complete set of fact names, each with a type, before any rule is compiled.
  • [OAR-FACT-2] An engine MUST reject at load a rule whose condition references an identifier that is not a declared fact or a declared observation function, naming the identifier. A mistyped fact name is a load failure, never a runtime default.
  • [OAR-FACT-3] An engine MUST reject at load a rule whose condition is not type-correct against the declared environment, and MUST reject a condition whose result type is not boolean. A rejection for a non-boolean result MUST name the type the condition produced and the word bool, so the author can see what the expression actually is.
  • [OAR-FACT-4] A fact is an observation, never a verdict. A fact provider MUST NOT publish a value that encodes a policy conclusion.
  • [OAR-FACT-5] A fact MUST NOT bake in a threshold, and MUST NOT combine other facts in a policy-meaningful way. The threshold and the composition are the policy, and they belong in the rule where a reviewer can read and change them.
  • [OAR-FACT-6] An engine MUST render effects only from the rule's declared effect and on_fire. Neither a fact provider nor a detector may render an effect.
  • [OAR-FACT-7] An engine MAY declare parameterized observation functions alongside plain facts, for observations that are only meaningful with an argument. An observation function MUST obey [OAR-FACT-4] and [OAR-FACT-5] exactly as a fact does.
  • [OAR-FACT-8] Condition evaluation MUST be free of side-effects: a condition MUST NOT mutate state and MUST NOT perform input or output. Every state change an engine performs is declared by on_fire.
  • [OAR-FACT-9] A fact whose production is expensive, asynchronous, or probabilistic — notably a detector-supplied fact — MUST be assembled lazily: an engine MUST NOT produce it unless a selected rule references it.
  • [OAR-FACT-10] flow matches when its steps appear, in order, as a subsequence of the recent activity window. The subsequence need not be contiguous. An engine MUST publish the size of that window as part of its profile.

5.1 Fact tiers

  • [OAR-FACT-11] Every fact an engine declares MUST carry exactly one tier: core, standard, or host.
  • [OAR-FACT-12] A conforming engine MUST provide every core fact, with the name, type, and observation meaning given in section 5.2.
  • [OAR-FACT-13] An engine claiming a named standard profile MUST provide every fact and function in that profile with the declared name, type, and meaning. An engine not claiming the profile MUST NOT declare a fact under one of its names.
  • [OAR-FACT-14] An engine MUST NOT redefine the name, type, or meaning of a core or standard fact.
  • [OAR-FACT-15] An engine MUST publish each host-tier fact under a namespace it owns, written <host>.<fact>, so that two engines cannot collide on a bare name. An engine MAY additionally accept the bare name inside its own deployment; a rule that uses the bare name is not portable.

6. Stateful effects

  • [OAR-FIRE-1] on_fire draws from a closed vocabulary: increment_counter, reset_counter, publish_event, increment_breaker, reset_breaker. An engine MUST reject a document naming any other side-effect.
  • [OAR-FIRE-2] An engine MUST apply a rule's on_fire actions only when that rule fired and its enforcement is enforce.
  • [OAR-FIRE-3] Counters maintained by an engine MUST be exposed to rules as ordinary facts, so a threshold on a counter is written in the rule and not in the engine.
  • [OAR-FIRE-4] A counter MUST be keyed by the rule identity and the session. An engine MAY expose additional counter scopes as host-tier facts.
  • [OAR-FIRE-5] Counter facts observed while a condition is evaluated MUST reflect the state before any side-effect of the current anchor occurrence is applied, so that a rule's own increment cannot change the value its own condition just read.

7. Operational semantics

  • [OAR-OPS-1] enforcement: monitor MUST evaluate the rule and record the outcome while producing no effect and applying no side-effect. It is the rollout path for a rule an operator is not yet ready to enforce.
  • [OAR-OPS-2] A rule cannot be evaluated when a fact provider fails, a detector fails, or its condition raises at run time. When a rule cannot be evaluated and its on_error is fail_closed, an engine MUST produce a block decision carrying that rule's identifier, and MUST NOT continue evaluating later rules at the occurrence.
  • [OAR-OPS-3] When a rule cannot be evaluated and its on_error is fail_open, an engine MUST record the failure and continue: the rule contributes no decision and no side-effect.
  • [OAR-OPS-4] When a rule cannot be evaluated and its on_error names a rule identifier, an engine MUST produce a block decision carrying that substituted identifier instead of the rule's own, and MUST NOT continue evaluating later rules at the occurrence. The substitution replaces the identifier only; the effect is block.
  • [OAR-OPS-5] A rule with mandatory: true MUST NOT be disabled, overridden, or removed by an overlay, a pack, or a caller. An engine MUST reject a configuration that attempts it.
  • [OAR-OPS-6] Evaluation of content anchors is buffered by default. An engine MAY support stream: chunk; one that does not MUST reject a document requesting it rather than silently buffering.
  • [OAR-OPS-7] An engine MUST record, per anchor occurrence, an applied-rules trace: for each selected rule, its identifier and its outcome — one of fired, passed, errored, or monitored. The trace is how an operator audits a decision.
  • [OAR-OPS-8] A rule with effect transform MUST produce a decision that identifies the content to be replaced and the replacement. An engine that does not implement content mutation MUST reject such a rule at load rather than treating it as a block.

7.1 Content-safety surface

Model input and output are anchors like any other, and a content-safety guardrail is an ordinary rule: a detector publishes observation facts, and the rule sets the threshold.

  • [OAR-OPS-9] A detector MUST return observations — scores, spans, entity lists — and MUST NOT return a verdict. The rule's condition owns every threshold.
  • [OAR-OPS-10] A detector reference is a URI of the form detector://<name>. An engine MUST reject a kind: detector rule whose reference it cannot resolve.

8. Portability profiles

Two profiles determine whether a rule travels: the anchor profile (which lifecycle moments a host has) and the fact profile (which observations it publishes).

  • [OAR-PROF-1] This specification fixes eight core anchors. Their identifiers and meanings are given in section 8.1 and MUST NOT be redefined by a host.
  • [OAR-PROF-2] A host MUST publish an anchor profile map declaring, for each core anchor, either the local anchor that implements it or that it is unsupported. Every core anchor MUST appear exactly once across the two declarations.
  • [OAR-PROF-3] An engine MUST resolve a rule whose on is a core anchor through the profile map before selection. A rule targeting a core anchor the host declares unsupported MUST be rejected at load, naming the anchor.
  • [OAR-PROF-4] A host MAY accept host-native on values naming anchors in its own catalogue. Such rules are valid OAR documents and MUST load; they are not portable.
  • [OAR-PROF-5] A rule is portable if and only if its on is a core anchor and its condition references only core-tier facts, facts from standard profiles it declares, and observation functions of those tiers. This specification promises identical behaviour across conforming engines for portable rules only.
  • [OAR-PROF-6] An engine MUST reject at load any rule listing in requires_facts a fact it does not provide, naming the rule and the fact.
  • [OAR-PROF-7] An engine SHOULD offer a portability report identifying, for a given rule, the host-native anchor or host-tier facts that make it non-portable. The report MUST NOT be a load failure — a non-portable rule is legal.

9. Conformance

9.1 The runner algorithm

The requirements below define the evaluation algorithm end to end. Each step is separately identified so a conformance fixture can cite it.

  • [OAR-CONF-1] Load each rule document and validate it against the published OAR schema. An engine MUST reject a document that fails validation, naming the failing field.
  • [OAR-CONF-2] An engine MUST reject a document whose spec_version major is unsupported, before any other processing of that document.
  • [OAR-CONF-3] An engine MUST resolve on: a core anchor identifier through the anchor profile map, any other value as a host-native anchor identifier.
  • [OAR-CONF-4] An engine MUST reject a rule whose requires_facts are not all provided by the host.
  • [OAR-CONF-5] An engine MUST type-check when against the declared fact environment and MUST reject the rule on an unknown identifier or a type error.
  • [OAR-CONF-6] At an anchor occurrence, an engine MUST select the rules whose resolved on matches and whose selector clauses all match.
  • [OAR-CONF-7] An engine MUST assemble the facts the selected rules reference. A fact provider failure MUST be handled per the rule's on_error.
  • [OAR-CONF-8] An engine MUST evaluate when. A rule with neither when nor flow fires whenever it is selected.
  • [OAR-CONF-9] An engine MUST record but not act on a rule whose enforcement is monitor: no effect, no side-effect, no short-circuit.
  • [OAR-CONF-10] An engine MUST order evaluation by kind then id, and the first enforced rule firing with block or transform MUST short-circuit the occurrence.
  • [OAR-CONF-11] An engine MUST apply decision precedence: block, then nudge, then warn, otherwise allow.
  • [OAR-CONF-12] An engine MUST apply the on_fire actions of every rule that fired and was enforced.

9.2 Fixture shape

  • [OAR-CONF-13] A conformance fixture is a JSON object with rule, input, and expected. rule is a rule document or a list of rule documents. input carries the anchor at which the occurrence happens and a facts map, and MAY carry recent_tools (the recent activity window flow matches against), session_id (the scope counters are keyed by), and profile (an anchor profile map). expected describes the outcome the engine MUST produce.
  • [OAR-CONF-19] When input.profile is present, an engine running the fixture MUST resolve the fixture's on values through that map instead of its own, and MUST otherwise behave exactly as it would for its own map. A fixture whose outcome depends on which core anchors a host supports MUST carry one — without it the fixture asks every implementation a different question, which the corpus promises never to do.
  • [OAR-CONF-14] A fixture MUST carry an id equal to its file name stem and a non-empty covers list of clause identifiers defined by this specification.
  • [OAR-CONF-15] expected MAY carry any of six keys, and a fixture asserts only the ones it is about. decision is the effect the occurrence resolves to, or none when nothing actionable is produced. code is the identifier the decision carries. on_fire lists the side-effects the winning rule declared. applied is the ordered applied-rules trace, each entry written <rule id>:<outcome> with the outcome one of fired, passed, errored, monitor. counters maps a rule identifier to the counter values expected after the occurrence. error asserts a load-time rejection and matches when the engine's error contains the given text; an engine MUST NOT be required to match error wording beyond that substring. An engine MUST reject a fixture carrying any other expected key rather than passing it silently.
  • [OAR-CONF-16] An implementation claiming conformance MUST pass every fixture in the published corpus whose clauses fall within the profiles it declares, and MUST report which fixtures it skipped and why.
  • [OAR-CONF-17] Every fixture in the published corpus MUST use core anchors and facts of core or standard tier only, so that a fixture can be run by an implementation that models no host-specific state.
  • [OAR-CONF-18] Three detector references are reserved for the corpus, and an engine running it MUST provide all three: detector://noop reports no findings; detector://error always fails, which is how a fixture reaches the on_error path; and detector://fixture reports no findings of its own, leaving the detector facts the fixture supplied in place, which is how a fixture proves the rule owns the threshold. None of the three requires a model or a network.

10. Extensibility and versioning

  • [OAR-DOC-26] A minor revision MUST be additive: it may add optional fields and enum members, and MUST NOT remove or rename a required field or change the decision an existing valid document produces.
  • [OAR-DOC-27] A change that breaks a valid document of the current major version MUST bump the major version.
  • [OAR-DOC-28] A published version of this specification is immutable. A correction MUST ship as a new version rather than an edit in place.
